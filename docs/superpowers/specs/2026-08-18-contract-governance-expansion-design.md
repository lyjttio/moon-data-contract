# MoonBit 数据契约治理流水线扩展设计

日期：2026-08-18
目标仓库：`lyjttio/moon-data-contract`
目标赛事：2026 年 8 月 MoonBit 黑客松结项扩展

## 1. 背景与目标

当前项目已经具备契约建模、Payload 校验、Schema Diff、兼容性检查、Registry、代码生成、报告、审计和基准能力，生产 MoonBit 源码为 4,063 行。申报书的后续方向包括 Kafka Schema Registry、GitHub PR 门禁 Bot 和更多格式适配器，但本阶段的验收环境要求可复现、可测试、可离线运行。

本次扩展实现一条可嵌入的离线数据契约治理流水线：对 Schema 版本快照进行策略化审计，生成发布门禁结果、风险评分和字段迁移计划，并输出 CI 可消费的结构化报告。目标是新增约 3,000–3,500 行有效生产 MoonBit 源码，使有效生产规模达到约 7,000–7,600 行，同时增加系统性边界测试和真实基准工作负载。

## 2. 非目标与约束

- 不实现 Kafka 网络协议、HTTP Schema Registry 服务端或 GitHub Bot 网络服务。
- 不引入未在当前工具链中验证的第三方网络依赖。
- 不把测试、生成的 `.mbti`、`_build` 产物或重复模板代码计入生产规模。
- CLI 新增命令只调用可验证的库 API 和确定性内置样例；不宣称已经具备 JSON 文件读取能力。
- 保持 wasm、wasm-gc、js 的可移植性；native 仅使用现有 CI 可稳定验证的路径。

## 3. 方案比较与选择

### 方案 A：离线契约治理流水线（采用）

复用现有 Registry、Diff、Compatibility、Audit 和 Report，增加快照、策略、迁移计划、发布门禁和 CI 输出。优点是形成完整业务闭环，代码可以由纯函数和结构化数据组成，容易测试、基准和跨后端验证。

### 方案 B：Kafka Schema Registry 协议优先

直接实现协议模型和服务适配。优点是对接场景清晰，缺点是网络、协议版本和认证会扩大范围，无法在本阶段保证所有目标后端的一致性。

### 方案 C：多格式适配器优先

扩展 JSON Schema、Avro、Proto 等导入/导出。优点是格式覆盖面大，缺点是容易形成多个孤立转换器，不能充分体现版本治理和发布门禁价值。

方案 A 被选中；未来 Kafka、Bot 和格式适配器可以作为治理流水线的外部输入/输出层接入。

## 4. 架构与模块

### 4.1 Snapshot：不可变版本快照

负责按 subject、version 管理 Schema 快照和版本轨迹。

- `SchemaSnapshot`：subject、版本、状态、来源、发布时间和 Schema。
- `SnapshotStore`：插入、按版本查询、latest 查询、范围查询和删除保护。
- 版本链分析：识别重复版本、非法版本、分支版本、跳跃版本和回滚候选。
- 确定性排序：报告和基准输出不依赖 Map 遍历顺序。

### 4.2 Policy：治理策略与例外

负责把业务发布规则转化为可执行结果。

- `GovernancePolicy`：兼容等级、允许/禁止的变更类别、风险阈值和必需审批项。
- 规则覆盖字段新增、删除、必填变化、类型变化、约束变化和版本升级。
- `PolicyException`：按 subject、字段或变更类别声明有界例外，并记录原因。
- 规则结果包含规则 ID、严重级别、证据和是否阻断发布。

### 4.3 Governance：发布门禁与风险聚合

将快照链、Policy 和现有 Compatibility/Audit 组合成发布决策。

- 对相邻版本和指定基线执行兼容性审计。
- 聚合错误、警告、例外、风险分数和建议版本升级。
- 输出 `GovernanceDecision`：允许发布、需人工审批或阻断发布。
- 支持单版本检查和整条版本链检查。
- 结果必须可重复：相同输入、策略和版本链产生相同决策与排序。

### 4.4 Migration：字段迁移计划

根据 Diff 和策略生成可执行的迁移计划，不执行真实数据变更。

- `MigrationPlan`：源版本、目标版本、动作列表、可逆性、风险和人工确认状态。
- 动作分类：复制字段、重命名映射、默认值填充、类型转换、约束确认、删除确认。
- 标记不可自动迁移的类型缩窄、必填字段新增和无默认值删除。
- 生成回滚检查，识别目标变更是否能安全反向应用。
- 迁移计划提供摘要和机器可读输出，便于未来接入 Bot 或流水线。

### 4.5 Report：治理报告

扩展现有报告体系，保持 Markdown、JSON、JUnit 等输出风格一致。

- 治理摘要：subject、基线、目标、策略、决策和风险等级。
- 版本轨迹：版本顺序、兼容性状态、阻断点和例外。
- 迁移摘要：动作数、自动化比例、人工确认项和回滚状态。
- JSON 字段保持稳定顺序和安全转义。
- JUnit 报告把阻断规则映射为失败，把警告映射为可见但不阻断的测试项。

### 4.6 CLI：可复现治理入口

新增命令仅包装核心库能力：

- `govern`：运行标准治理样例并输出发布门禁报告。
- `snapshot`：展示标准版本链和版本轨迹摘要。
- `plan`：生成标准 Schema 演化的迁移计划。
- `policy`：展示内置策略及规则结果。

旧有 `benchmark` 和 `audit` 命令保持兼容。CLI 帮助文本明确哪些命令是内置样例/预览，避免把路径参数误称为已完成的文件解析。

## 5. 数据流

```text
Schema snapshots
       │
       ▼
Version-chain analysis ──► duplicate/branch/gap findings
       │
       ▼
Compatibility + GovernancePolicy
       │
       ├──► GovernanceDecision ──► release gate
       ├──► MigrationPlan ────────► manual/automatic actions
       └──► GovernanceReport ─────► Markdown/JSON/JUnit/CLI
```

所有模块通过显式结构体和纯计算接口连接；报告层不反向修改 Registry 或策略，迁移计划也不执行外部副作用。

## 6. 测试策略

采用测试先行，每个模块先添加失败测试，再实现最小功能，最后执行全目标验证。

边界测试覆盖：

- 空 Registry、空 subject、重复 subject/version、非法 SemVer；
- 单版本、非线性版本链、跳跃版本、重复版本和回滚候选；
- 新增/删除必填字段、类型缩窄/放宽、约束收紧/放宽、嵌套结构变更；
- 策略阈值上下界、多个规则同时触发、例外匹配与无效例外；
- 迁移冲突、无默认值填充、不可逆类型转换、回滚失败；
- 深层嵌套、宽 Schema、Unicode 字段、稳定排序和重复运行一致性；
- JSON/JUnit 输出中的引号、反斜杠、换行和空结果。

测试必须验证真实治理结果、阻断原因、动作分类和报告内容，不用 mock 替代现有 Diff、Compatibility 或 Validator 核心逻辑。

## 7. Benchmark 与规模验收

新增四类确定性工作负载：版本链扫描、策略评估、迁移计划生成、治理报告渲染。每类记录固定操作数、核心单调时钟耗时和脚本 wall-clock 样本；报告注明目标后端、工具链、操作数、机器和样本数。

验收脚本统计 `.mbt` 的有效生产行（排除空行与注释），同时报告物理生产行、测试源码和总量。目标为有效生产 7,000–7,600 行、物理生产行保持 7–8 千、测试文件不少于 55 个，所有新增行必须属于快照、策略、治理、迁移、报告、CLI 或测试支持的可复用实现。

## 8. 验证与交付

本地验证顺序：`moon fmt --check`、`moon info`、`moon check --deny-warn`、wasm/wasm-gc/js 测试、验收统计脚本、benchmark 脚本和 CLI 样例命令。之后执行 GitHub Actions 的稳定工具链 CI，确认远程 `main` 与唯一贡献者约束不变；仅在验证完成后更新 README、申报书指标并发布新的 Mooncakes 版本。
